## Routing Rules

- Use `research` for research-before-implement: investigate, fact-find, evaluate technologies, compare alternatives, or review literature before committing to implementation.
- Implementation orchestrators (`burp-tls-orchestrator`, `senior-rust-orchestrator`) should delegate pre-implementation research to `research` and read `_workspace/05_report.md` before dispatching to their specialists.
- Use `burp-tls-orchestrator` for end-to-end design, implementation, refactoring, verification, or follow-up changes to this project.
- Use the orchestrator even for small follow-ups if the request touches more than one boundary: Montoya API, Kotlin UI, Rust core, UniFFI, Gradle packaging, or QA.
- The Burp TLS orchestrator delegates non-trivial Kotlin/Swing UI, Burp Settings panel, Preferences-backed extension configuration, and screenshot-informed UI work to `burp-suite-ui-engineer`.
- Use `ja4-browser-capture-orchestrator` for empirical browser JA4 capture and bot-score validation. It may use Wireshark/tshark, Firefox DevTools MCP, Chrome DevTools MCP, Playwright MCP, bash-driven Playwright, and Cloakbrowser profiles. Do not limit Playwright to a single browser when user/profile definitions provide more browsers.
- When TLS profile, JA4/JA3, proxy TLS, or browser fingerprint behavior changes, include JA4 browser capture QA: primary target `https://cloudflare.manfredi.io/test/`, desired result `You are not a verified bot` with human percentage as high as possible, plus secondary bot/fingerprint sites documented by the harness.
- Use `senior-rust-orchestrator` for Rust-only implementation, review, debugging, refactoring, performance, unsafe/FFI, Cargo, crate, test, clippy, or architecture tasks.
- The Rust harness is linked to existing project agents: `senior-rust-orchestrator` may Task `rust-tls-core-engineer` for TLS/fingerprint Rust work and `burp-tls-qa` for extension-boundary verification; `burp-tls-orchestrator` may Task `senior-rust-engineer` for senior Rust review inside the Burp TLS extension workflow.
- The Deep Research harness fans out to `web-researcher`, `academic-researcher`, `community-researcher`, and `research-synthesizer`. Its reports feed into implementing orchestrators.
- Direct specialist invocation by `@mention` is acceptable only when the user explicitly asks for one narrow specialist result.
- Do not create a custom `general`, router, team, or peer-messaging agent. Coordination happens through the orchestrator Task calls and `_workspace/` files.
- Prefer current official documentation for exact API signatures: PortSwigger Montoya Javadoc, PortSwigger extension docs, Mozilla UniFFI guide, Kotlin/Gradle docs, and crate docs for chosen Rust TLS libraries.
- For complex parsing/protocol work, especially raw request/response parsing, require library research first. Prefer maintained crates or existing project dependencies; only write custom parsers after documenting why no library fits, and avoid ad hoc manual `while`-loop parsing in favor of idiomatic Rust parser/state-machine patterns with tests.
